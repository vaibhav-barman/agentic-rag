## Module 2: BYO retrieval + memory

**Migration `0004_byo_retrieval.sql`**
- Option A cleanup (drops listed above).
- `documents`: add `storage_path text`, `file_size bigint`, `mime_type text`, `updated_at timestamptz`; status check becomes `pending | processing | completed | failed`.
- Private Storage bucket `documents`; `storage.objects` policies for select/insert/delete limited to paths starting with `auth.uid()/`.
- `alter publication supabase_realtime add table public.documents` (RLS filters the events per user).
- `match_document_chunks` gains `match_threshold float` (rows below it are dropped).
- `messages.steps jsonb` (tool-step trace, used from Module 7 on).

**Backend**
- `POST /documents`: validate, upload bytes to Storage at `{user_id}/{document_id}/{filename}`, insert row `pending`, schedule `process_document` with `BackgroundTasks`, return `201` immediately.
- `ingestion.process_document(repo, document)`: `processing` -> download -> parse -> chunk -> embed -> insert chunks -> `completed` (or `failed` + error). Blocking parse/Supabase calls go through `asyncio.to_thread`.
- `DELETE /documents/{id}` also removes the Storage object.
- Config: `RETRIEVAL_MIN_SIMILARITY` (default 0.3), passed to the RPC. Chat already stores history and sends the last `CHAT_HISTORY_LIMIT` messages; unchanged.
- Remove OpenAI-era comments/fields from code, `test_rls.py`, README.

**Frontend** (`pages/Ingestion.tsx`)
- Subscribe to `postgres_changes` on `documents` with supabase-js; apply INSERT/UPDATE/DELETE to the list; drop the local "uploading" placeholder rows once the server row exists. Status badges: pending, processing (spinner), completed, failed.

**Validation**
- pytest: upload returns `pending` and a Storage write; background task ends `completed` with chunks; parse/embed failure -> `failed`; delete removes Storage object; threshold forwarded to `match_chunks`.
- Integration (`pytest -m integration`): user B cannot read A's Storage object or chunks; `user_vector_stores` gone.
- Playwright: upload shows `processing` then `completed` without a page reload or refetch (assert no `GET /documents` after the upload response).

## Module 3: Record manager

**Migration `0005_record_manager.sql`**: `documents.content_hash text`, index `(user_id, content_hash)`, unique `(user_id, filename)` (existing duplicates get a ` (n)` suffix first); `document_chunks.content_hash text`.

**Backend** - `services/record_manager.py`:
- `decide(repo, filename, sha256)` -> `unchanged` (same filename and hash, completed: nothing is processed), `duplicate` (same hash under another filename: nothing is processed, existing doc returned), `updated` (same filename, new hash), `created`.
- `updated` path does a chunk-level diff by chunk hash: keep matching chunks (fix `chunk_index`), embed only new chunks, delete stale ones.
- Upload response adds `action`; `200` for unchanged/duplicate/updated, `201` for created.

**Frontend**: toast per upload ("Already up to date", "Same content as X", "Updated: 2 of 9 passages re-embedded").

**Validation** - pytest: same file twice -> one document, `embed` called once; edited file -> only changed chunks embedded, stale removed, count correct; same bytes under a new name -> `duplicate`. Playwright: re-upload shows the "already up to date" toast and the list still has one row.

## Module 4: Metadata extraction

**Migration `0006_metadata.sql`**: `documents.metadata jsonb not null default '{}'` + GIN index; retrieval RPC gains `filter jsonb` (`d.metadata @> filter`) and `filename_filter text`.

**Backend**
- `schemas.DocumentMetadata` (Pydantic): `title`, `summary`, `document_type` (Literal: report, article, notes, manual, contract, email, resume, spreadsheet, other), `topics: list[str]` (lowercased, max 8), `language`, `key_entities: list[str]`, `document_date: date | None`.
- `llm.complete_structured(messages, model_cls)`: non-streaming `chat.completions.parse(response_format=model_cls)`, `@traceable`; validated with Pydantic.
- `services/metadata.py`: extract from the first ~8,000 chars during ingestion. Failure is non-fatal (document still completes, metadata `{}`).
- `file_search` tool gains optional `document_type`, `topic`, `filename` arguments, turned into the RPC filter. The system prompt lists the user's document types and topics so the model knows valid filter values.

**Frontend**: document rows show type badge, topics and the summary.

**Validation** - pytest: metadata stored from a scripted structured reply; invalid reply -> document still `completed`; tool call with `document_type` reaches `match_chunks` as the right filter. Integration: RPC with a filter returns only matching documents. Live: upload two different kinds of file, ask a question restricted to one type, sources only from it.

- Allowed types and the upload page's accept list/copy updated; max size unchanged.
- Cascade deletes: `document_chunks` already cascades from `documents` and from `auth.users`. Add an integration test proving document delete removes chunks and the Storage object, and extend it to user deletion.
- No migration.

**Validation** - pytest with small generated fixtures (DOCX via python-docx, HTML string, Markdown, PDF): each yields expected text; corrupt file -> `failed` with a readable error. Playwright: upload an `.html` and a `.docx`, both reach `completed`, a question is answered from the DOCX.

## Module 6: Hybrid search + reranking

**Migration `0007_hybrid_search.sql`**: `document_chunks.fts tsvector generated always as (to_tsvector('english', content)) stored` + GIN; RPC `hybrid_search_chunks(query_text, query_embedding, match_count, filter, filename_filter, document_id_filter, rrf_k default 60)` (security invoker): keyword leg (`websearch_to_tsquery`) and vector leg, fused with Reciprocal Rank Fusion, returning both ranks and the RRF score.

**Backend** - `services/retrieval.py` (owns search; `chat.file_search` moves here):
- `SEARCH_MODE=hybrid|vector|keyword`, `RETRIEVAL_CANDIDATES=20`, `FILE_SEARCH_TOP_K=5`, `RERANK_ENABLED=true`, `RERANK_MIN_SCORE=0.2`.
- `rerank(query, candidates)`: one `complete_structured` call returning `[{index, score 0-1}]`; keep top-k above the minimum score. On any failure, fall back to RRF order.
- Sources carry `score`, `vector_rank`, `keyword_rank`.

**Validation** - pytest: RRF order from fake legs; rerank reorders and drops low scores; rerank failure falls back. Integration: a chunk containing an exact rare token (e.g. `XK-7741-Q`) is returned for that query through the keyword leg; RLS holds on the new RPC. Live: ask for the exact code and get the right source.

## Module 7: Additional tools

**Migration `0008_readonly_sql.sql`**: `execute_readonly_sql(query text) returns jsonb` - security invoker (so RLS applies), rejects anything that is not a single `select`/`with` statement or that references schemas other than `public`, sets a 5s `statement_timeout`, wraps the query to return at most 100 rows as JSON. Executable by `authenticated` only.

**Backend**
- `services/tools/` registry: each tool = JSON schema + `available(ctx)` + async executor that yields UI events and returns a result. `chat.run_chat_turn` loops over the registry instead of hard-coding `file_search`. `MAX_TOOL_ROUNDS` default raised to 6.
- `query_database(sql)`: tool description carries the queryable schema (columns of `documents`, `document_chunks` without `embedding`, `threads`, `messages`). Validated in Python as well as in the RPC. Result rows returned to the model and shown in the UI with the SQL used.
- `web_search(query)`: Tavily `POST /search` via `httpx`, top 5 results (title, url, snippet). Only offered when `TAVILY_API_KEY` is set. System prompt: documents first, web only when they lack the answer, and say which was used.
- Sources gain `type: document | web | sql`, `url`, `title`. New SSE events `tool_call {id, name, arguments, parent_id}` and `tool_result {id, ok, summary, parent_id}`; the trace is saved in `messages.steps`.

**Frontend**: `components/chat/ToolSteps.tsx` - collapsible step timeline above each answer (tool, arguments, result summary; SQL shown as code, rows as a small table). Web sources render as links in the source margin. Steps reload from history.

**Validation** - pytest: registry routing; `query_database` rejects `delete`, multi-statement and `auth.` references; web tool hidden without key; Tavily response mapped to sources (httpx mocked); steps persisted. Integration: `execute_readonly_sql` returns only the caller's rows and refuses writes. Live/Playwright: "How many documents have I uploaded?" shows a `query_database` step and the right count; with a Tavily key, a current-events question shows a web source link.

## Module 8: Sub-agents

**Migration `0009_document_content.sql`**: `documents.content text` (full parsed Markdown, written at ingestion; never selected in list queries).

**Backend** - `services/subagent.py`:
- Main-agent tool `analyze_document(document_id, task)`, described for whole-document work (summarise, compare, extract everything, "read the whole thing"). The system prompt lists the user's documents (id, filename, type, summary; capped at 50) so the model can pick one.
- The sub-agent runs with an isolated context: its own system prompt, the task, and the full document text (up to `SUBAGENT_MAX_CHARS`, default 400k; beyond that an outline plus tools). Its own tools: `search_in_document(query)` (hybrid search with `document_id_filter`) and `read_passages(start, end)`. Own loop, `SUBAGENT_MAX_ROUNDS=4`. None of the main conversation history is passed in, and only its final answer returns to the main agent.
- Its `tool_call` / `tool_result` events and streamed text (`subagent_delta`) carry `parent_id` = the main agent's `analyze_document` call id. Traced as a nested `sub_agent` run in LangSmith.

**Frontend**: `ToolSteps` renders children nested under the `analyze_document` step with the sub-agent's streamed text and its own steps, visually indented and labelled "Sub-agent".

**Validation** - pytest: scripted main LLM calls `analyze_document`; assert the sub-agent's messages contain the document text and none of the main history, events carry `parent_id`, final text returned as the tool result, nested steps persisted. Playwright (live): "Summarise the whole of <file>" shows a nested sub-agent block with at least its streamed text, and the answer reflects content from both the start and end of the file.
