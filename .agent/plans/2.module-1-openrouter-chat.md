# 2. Module 1 (rest): OpenRouter Chat, File Search, LangSmith

**Complexity:** ⚠️ **Medium** - three phases, run in order, validate after each. Replaces Phases B-D of `1.module-1-app-shell.md` (Phase A stays as built).

| Phase | Complexity |
|---|---|
| B. Threads + memory + streaming chat | ⚠️ Medium |
| C. Upload + file_search tool | ⚠️ Medium |
| D. LangSmith tracing | ✅ Simple |

## Why this replaces plan 1
The provider is OpenRouter, not OpenAI. OpenRouter is stateless and has no `previous_response_id` or hosted vector stores, so:
- **Memory:** messages are stored in Supabase and the last N are sent with each request.
- **File search:** a `file_search` tool the model can call, backed by chunks + embeddings in Supabase pgvector.

## Decisions
- LLM calls: `openai` Python SDK with `base_url=OPENROUTER_BASE_URL` (raw SDK, no LangChain). All LLM code lives in `backend/app/services/llm.py`.
- Chat model: `OPENROUTER_MODEL` (default `openai/gpt-4.1-mini`, must support tool calling). Embeddings: `OPENROUTER_EMBEDDING_MODEL` (default `openai/text-embedding-3-small`, 1536 dims) via OpenRouter's `/embeddings`.
- History window: last 20 messages (`CHAT_HISTORY_LIMIT`).
- Backend talks to Supabase **as the user** (anon key + user JWT) so RLS applies; the service-role key is only used in tests.
- Ingestion is synchronous in the upload request (Realtime status is Module 2). Allowed: `.txt`, `.md`, `.pdf` (via `pypdf`), max 10 MB.
- Chunking: ~800 tokens approximated as 3200 chars with 400-char overlap.

## Phase B: Threads + Memory + Streaming Chat

### B.1 Migration `0002_openrouter.sql`
- Drop `threads.last_response_id`, `documents.openai_file_id`, table `user_vector_stores`.
- **Validation:** applied in SQL Editor; `pytest -m integration` still passes (update `test_rls.py` to drop `user_vector_stores`).

### B.2 Supabase client per request
- `app/db.py`: `user_client(user)` -> supabase client with anon key and `Authorization: Bearer <user jwt>` on PostgREST.
- **Validation:** unit test that the client sends the user's token.

### B.3 Thread endpoints
- `POST /threads`, `GET /threads` (newest first), `GET /threads/{id}/messages`, `DELETE /threads/{id}`.
- **Validation:** pytest with a fake DB layer: create/list/fetch/delete; unknown or foreign id -> 404. Integration: user B gets 404 on A's thread.

### B.4 LLM service + chat endpoint (SSE)
- `llm.stream_chat(messages, tools)` async generator over `chat.completions.create(stream=True)` yielding text deltas and tool calls.
- `POST /threads/{id}/chat {content}`: save user message, load last N messages, stream; SSE events `delta {text}`, `sources {...}` (Phase C), `done {message_id}`, `error {message}`. Persist the assistant message at the end; set title from the first message if empty.
- **Validation:** pytest with LLM mocked: SSE order, both messages persisted, history sent includes earlier turns, title set. Live: "My name is Ada" then "What's my name?" -> answer contains Ada.

### B.5 Chat UI
- Left sidebar: New chat, thread list (title, select, delete). Main: message list (markdown via `react-markdown`), auto-scroll, input (Enter sends, Shift+Enter newline), streaming render, stop/disable while streaming. SSE read with `fetch` + stream reader.
- **Validation (Playwright, real backend + OpenRouter):** send message -> text streams in; reload keeps history; two threads show their own messages; follow-up keeps context.

## Phase C: Upload + file_search Tool

### C.1 Migration `0003_document_chunks.sql`
- `create extension vector`; `document_chunks (id, document_id fk cascade, user_id, chunk_index, content, embedding vector(1536))`, HNSW cosine index, RLS own-rows.
- `match_document_chunks(query_embedding vector, match_count int)` SQL function, `security invoker` (RLS applies), returns content, filename, similarity.
- **Validation:** integration test: A's chunks never returned to B's search.

### C.2 Ingestion service + endpoints
- `services/ingestion.py`: extract text, chunk, embed in batches, insert chunks, set `documents.status` to `completed` / `failed`.
- `POST /documents` (multipart), `GET /documents`, `DELETE /documents/{id}` (chunks cascade).
- **Validation:** pytest with embeddings mocked: chunking boundaries/overlap; upload -> chunks stored, status completed; bad type -> 415; too big -> 413; foreign delete -> 404.

### C.3 file_search tool in chat
- Tool `file_search(query)` offered when the user has >=1 completed document. On a tool call: embed query, `match_document_chunks` top 5, return excerpts with filenames, feed back, continue streaming. Emit `sources` SSE event; UI shows source chips under the answer.
- **Validation:** pytest with LLM mocked to call the tool: tool result sent back, sources event emitted. Live: upload a file containing a made-up fact, ask about it, answer uses it and shows the source; delete file, ask again, fact gone.

### C.4 Ingestion UI
- Drag-and-drop zone + file picker, upload progress/status, document list (name, status, date) with delete.
- **Validation (Playwright):** drop a .txt, see `completed`, delete, see it gone.

## Phase D: LangSmith Tracing
- `pip install langsmith`; wrap the client in `llm.py` with `langsmith.wrappers.wrap_openai`; `@traceable` on the chat turn with metadata `user_id`, `thread_id`, `file_search_used`. Tracing off when `LANGSMITH_TRACING=false`.
- **Validation:** tests pass with tracing off; one live chat produces a trace in `LANGSMITH_PROJECT` with inputs, streamed output, model, token usage, metadata (check via LangSmith API).

## End-to-end
Start backend + frontend, log in, upload a doc, ask about it in a new thread, get a streamed grounded answer with a source, follow-up keeps context, reload keeps history, trace visible in LangSmith. Update `PROGRESS.md` and commit after each phase.
